# 企业 API Key 管理方案草案

## 背景

本方案用于在 new-api 现有能力基础上增加企业级 API Key 管理。目标不是重做管理后台风格，而是在保留现有页面风格、交互习惯和权限体系的前提下，让一个企业主账户统一管理多个成员账户的 API Key、用量和账单归属。

截图仅作为功能参考，不作为视觉风格参考。前端实现时应继续沿用当前默认前端的布局、组件、表格、筛选器、按钮和提示风格。

## 目标

- 企业主账户可以创建、启用、禁用和管理多个成员账户。
- 成员账户可以登录并管理自己的 API Key。
- 成员账户可以查看自己的 API Key 用量、调用日志和基础状态。
- 成员账户产生的消耗统一从企业主账户余额或额度中扣除。
- 企业主账户可以查看所有成员账户的汇总用量、单个成员用量、API Key 状态和调用日志。
- 现有普通用户、管理员、渠道、倍率、模型、日志和计费逻辑尽量复用，减少对既有流程的破坏。

## 非目标

- 第一阶段不重做注册、登录、管理员后台或整体 UI 主题。
- 第一阶段不支持一个成员同时加入多个企业。
- 第一阶段不支持复杂组织架构、部门树、审批流或多级管理员。
- 第一阶段不改变现有系统管理员对全站用户和配置的最高管理能力。
- 第一阶段不暴露明文 API Key 给企业主，除非后续明确确认安全策略。

## 术语

| 名称 | 含义 |
| --- | --- |
| 企业主账户 | 统一承担计费和成员管理的账户。用户描述中的“超级账户”建议在产品文案中称为“企业主”或“企业账户”，避免和系统超级管理员混淆。 |
| 成员账户 | 归属于企业主账户的普通用户。成员可以拥有自己的 API Key，并只能查看自己的数据。 |
| 计费归属账户 | 实际扣费的用户。非企业场景下等于请求发起用户；企业场景下等于企业主账户。 |
| 请求发起用户 | API Key 所属用户，用于权限、日志展示和成员维度统计。 |
| 系统管理员 | 现有后台管理员/root 角色，仍然拥有全站管理权限，不等同于企业主账户。 |

## 角色与权限

### 企业主账户

- 可以查看企业整体用量概览。
- 可以创建成员账户，或将已有普通账户加入企业。
- 可以禁用、移除、重置成员状态。
- 可以查看成员列表、成员用量、成员调用日志和成员 API Key 元数据。
- 可以设置成员级别的用量上限、模型权限或分组策略，具体是否进入第一阶段待确认。
- 不建议默认查看成员 API Key 明文，只允许禁用、删除或触发重置。

### 成员账户

- 可以登录现有控制台。
- 可以创建、禁用、删除自己的 API Key。
- 可以查看自己的用量、日志、额度消耗明细和错误信息。
- 不可以查看企业主余额、其他成员、企业总账单或其他成员日志。
- 不可以脱离企业主单独扣费，除非后续增加独立余额策略。

### 系统管理员

- 保持现有系统管理员能力。
- 可以查看和处理全站用户、企业主账户、成员账户、渠道和日志。
- 可以为企业关系做兜底维护，例如解绑异常成员、修正计费归属。

## 核心流程

### 企业主创建成员

1. 企业主进入“企业管理”页面。
2. 点击“新增成员”。
3. 填写成员用户名、邮箱、初始密码或邀请方式。
4. 系统创建成员用户，并建立企业主与成员之间的关系。
5. 成员登录后进入普通控制台，只看到自己的 API Key 和用量。

### 成员使用 API Key

1. 成员创建自己的 API Key。
2. 客户端使用该 API Key 请求接口。
3. 鉴权阶段识别 API Key 所属用户为成员账户。
4. 计费阶段识别该成员的计费归属账户为企业主账户。
5. 预扣费、结算、失败回滚和日志落库都写入成员维度与企业主维度。
6. 成员页面展示自己的请求记录，企业主页面展示企业汇总和成员明细。

### 企业主查看用量

1. 企业主进入“企业用量”页面。
2. 默认查看全企业汇总：请求数、消耗额度、成功率、模型分布、时间趋势。
3. 可以按成员、API Key、模型、渠道、时间范围筛选。
4. 可以进入某个成员详情页查看该成员用量和 API Key 元数据。

## 数据模型建议

实际字段命名可在实现时调整，但应遵守跨 SQLite、MySQL、PostgreSQL 的兼容要求，优先通过 GORM 定义模型和索引，避免数据库特有 SQL。

### enterprise_accounts

表示企业账户关系的主表。

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| owner_user_id | 企业主用户 ID，唯一索引 |
| name | 企业名称，可默认为企业主用户名 |
| status | 企业状态，例如 enabled、disabled |
| created_at / updated_at | 创建和更新时间 |

### enterprise_members

表示企业主与成员之间的关系。

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| enterprise_id | 企业 ID |
| owner_user_id | 冗余企业主用户 ID，便于查询和校验 |
| member_user_id | 成员用户 ID，v1 建议唯一，避免多企业归属 |
| role | 成员角色，v1 可先固定为 member |
| status | 成员状态，例如 active、disabled、removed |
| display_name | 企业内展示名，可选 |
| created_at / updated_at | 创建和更新时间 |

建议索引：

- `owner_user_id`
- `member_user_id`
- `enterprise_id + status`
- `owner_user_id + member_user_id`

### 用户表扩展

可选增加冗余字段以降低高频查询成本。

| 字段 | 说明 |
| --- | --- |
| enterprise_id | 成员所属企业 ID，普通用户为空 |
| billing_owner_user_id | 计费归属用户 ID，普通用户为空或等于自身 |

是否直接扩展用户表需要结合现有查询路径确认。如果希望减少迁移风险，也可以先只依赖 `enterprise_members` 表，在鉴权和计费阶段通过缓存解析计费归属。

### 日志表扩展

为了支持企业主按成员统计，建议日志保留两类用户 ID。

| 字段 | 说明 |
| --- | --- |
| user_id | 请求发起用户，即 API Key 所属成员 |
| billing_user_id | 实际扣费用户，企业场景下为企业主 |
| enterprise_id | 企业 ID，非企业场景为空 |
| token_id | API Key 对应 token ID，复用现有字段优先 |

兼容策略：

- 老日志没有 `billing_user_id` 时，按 `user_id` 处理。
- 非企业请求中 `billing_user_id` 可为空或等于 `user_id`，查询时统一归一化。

## 计费与结算设计

企业功能的关键是区分“谁发起请求”和“谁承担费用”。

### 鉴权阶段

- API Key 仍然归属于成员账户。
- 鉴权后上下文中保留请求发起用户 ID。
- 如果用户属于企业成员，则解析出企业主账户作为计费归属账户。
- 建议将企业关系放入缓存，避免每次请求都直接查询数据库。

### 预扣费阶段

- 预扣费读取计费归属账户余额或额度。
- 成员自身余额不参与扣费，除非后续明确支持成员独立余额。
- 如果企业主余额不足，应返回余额不足，日志仍记录成员维度。

### 结算阶段

- 实际消耗从企业主账户扣除。
- 结算日志同时写入成员用户 ID、企业主用户 ID 和企业 ID。
- 回滚逻辑也应作用于企业主账户。

### 报表阶段

- 成员查询：按 `user_id = 当前成员` 过滤。
- 企业主查询：按 `billing_user_id = 当前企业主` 或 `enterprise_id = 当前企业` 过滤。
- 系统管理员查询：保留现有全局查询能力，并可额外按企业筛选。

## API 设计建议

路由命名仅作为草案，实际实现时应结合现有 router/controller 风格调整。

### 企业主接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/enterprise/summary` | 企业用量与成员概览 |
| GET | `/api/enterprise/members` | 成员列表 |
| POST | `/api/enterprise/members` | 创建成员 |
| PATCH | `/api/enterprise/members/:id` | 更新成员状态或展示信息 |
| DELETE | `/api/enterprise/members/:id` | 移除成员关系或禁用成员 |
| GET | `/api/enterprise/members/:id/usage` | 查看单个成员用量 |
| GET | `/api/enterprise/members/:id/tokens` | 查看单个成员 API Key 元数据 |
| GET | `/api/enterprise/logs` | 企业维度调用日志 |

### 成员接口

成员优先复用现有 token、日志和用量接口。

- 创建 API Key：复用现有 token 创建接口。
- 查看 API Key：复用现有 token 列表接口。
- 查看用量日志：复用现有日志接口，但后端自动限制为当前成员。
- 查看企业归属状态：可增加轻量接口，例如 `/api/user/enterprise-status`。

### 系统管理员接口

系统管理员后台可增加企业筛选和维护能力。

- 查询企业列表。
- 查询企业成员。
- 修正企业关系。
- 禁用企业或企业成员。

## 前端页面规划

保持 new-api 现有默认前端风格，不引入截图中的视觉风格。

### 企业主视角

建议在控制台侧边栏新增“企业管理”入口。

页面模块：

- 企业概览：总请求数、总消耗、成员数、活跃 API Key、近 7/30 天趋势。
- 成员管理：成员列表、状态、创建时间、最近调用时间、累计消耗。
- 成员详情：成员基础信息、API Key 元数据、用量趋势、调用日志。
- 企业日志：按成员、API Key、模型、状态、时间筛选。
- 设置：企业名称、成员默认权限、是否允许成员自助创建 API Key。

### 成员视角

成员继续使用现有“令牌/API Key”“日志”“用量”等页面。

页面需要补充：

- 顶部或资料页展示“已加入企业”状态。
- 余额/额度展示应避免误导，可显示“由企业账户统一结算”。
- 成员只能看到自己的 API Key 和调用日志。

### 系统管理员视角

在用户管理或独立企业管理页面中增加：

- 企业主标识。
- 企业成员数量。
- 企业状态。
- 快速进入企业详情。

## 迁移与兼容

- 现有用户默认不是企业主，也不是企业成员。
- 现有 API Key 默认按 API Key 所属用户扣费。
- 只有建立企业成员关系后，成员请求才改为企业主扣费。
- 老日志无需强制迁移；查询时对缺失 `billing_user_id` 的日志按 `user_id` 兼容。
- 如增加用户表字段，迁移必须兼容 SQLite、MySQL 和 PostgreSQL。
- 企业功能可以通过系统设置开关控制，便于灰度发布和回滚。

## 安全与审计

- 企业主不能默认查看成员 API Key 明文。
- 成员移除企业后，其 API Key 的处理方式需要明确：禁用、保留但恢复个人扣费，或强制删除。
- 企业主创建、禁用、移除成员需要记录审计日志。
- API Key 创建、禁用、删除、重置需要记录审计日志。
- 企业主查看成员日志属于敏感操作，建议记录操作人和时间。
- 成员不能通过接口参数伪造 `billing_user_id`、`enterprise_id` 或 `owner_user_id`。

## 边界情况

- 企业主余额不足：成员请求失败，错误提示应说明企业账户额度不足。
- 成员被禁用：成员登录和 API Key 请求都应被阻止，具体策略可配置。
- 企业被禁用：企业主和所有成员的企业扣费请求都应被阻止。
- 成员被移除：需要决定成员 API Key 是否立刻失效。
- 企业主被删除或降权：需要先处理企业成员关系，避免孤儿关系。
- 成员已有个人余额：v1 建议不自动合并，不自动转移。

## 分阶段实施建议

### Phase 1：方案与基础模型

- 完成 Markdown 方案确认。
- 明确术语、权限、字段和边界规则。
- 增加企业关系模型、迁移和基础查询方法。
- 不改变现有计费路径。

### Phase 2：后端接口与权限

- 增加企业主成员管理接口。
- 增加企业用量和企业日志查询接口。
- 增加成员归属状态接口。
- 补充权限校验和审计日志。

### Phase 3：计费路径接入

- 在 API Key 鉴权后解析计费归属账户。
- 将预扣费、结算、回滚切换为使用计费归属账户。
- 日志写入请求发起用户和计费归属用户。
- 补充企业维度统计查询。

### Phase 4：前端页面

- 增加企业管理入口。
- 实现企业概览、成员管理、成员详情和企业日志页面。
- 调整成员视角的余额/用量文案。
- 按现有 i18n 体系补齐多语言文案。

### Phase 5：增强能力

- 成员级用量上限。
- 成员级模型或渠道权限。
- 邀请链接和邮箱邀请。
- 企业审计日志页面。
- 企业账单导出。

## 待确认问题

- 成员是否必须能登录控制台，还是也需要支持 API-only 成员？
- 企业主是否可以查看成员 API Key 明文，还是只能禁用、删除、重置？
- 成员离开企业后，已有 API Key 是禁用、删除，还是恢复个人扣费？
- 成员是否允许拥有个人余额？
- 是否需要成员级额度上限和模型白名单进入第一版？
- 企业主是否可以把已有用户加入企业，还是只能创建新用户？
- 是否需要邀请流程，还是第一版由企业主直接创建账号？
- 企业名称、企业头像、企业标识是否需要独立配置？

## 初步验收标准

- 企业主可以创建至少一个成员账户。
- 成员可以创建自己的 API Key 并成功请求接口。
- 成员请求产生的消耗扣到企业主账户。
- 成员只能看到自己的 API Key 和用量。
- 企业主可以看到所有成员的汇总和明细用量。
- 非企业用户行为与现有系统保持一致。
- 系统管理员仍可按现有方式管理全站用户和日志。
