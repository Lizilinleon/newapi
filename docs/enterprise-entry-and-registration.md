# 企业版入口与简化注册方案（草案）

## 背景

当前已经有一版企业 API Key 管理能力，下一步希望把整个程序的默认入口切到这一版企业管理视图，而不是继续把原来的系统仪表盘当作首页。

同时，登录/注册流程也要收敛成一套更简单的方案，尽量保留原来删掉部分里“最有用、最轻量”的部分，先跑通最基础的企业使用闭环。

## 目标

- 打开程序后，默认看到企业管理页面
- 登录成功后，统一进入企业管理首页
- 保留 new-api 现有的页面风格和组件体系，只调整默认入口和注册闭环
- 注册流程尽量简单，先只保留最小可用能力
- 不在第一版恢复 OAuth、Passkey、2FA、邮箱验证码、复杂找回密码等功能

## 1. 入口调整方案

### 1.1 首屏决策

建议把“首屏”拆成三层判断：

1. 先检查系统是否完成初始化
2. 再检查当前是否已登录
3. 最后决定进入企业页还是登录页

对应行为建议如下：

- 未初始化：进入 `/setup`
- 已初始化但未登录：进入 `/sign-in`
- 已初始化且已登录：进入 `/enterprise`

### 1.2 登录后的默认落点

登录成功后，不再进入原来的 dashboard，而是统一跳转到企业管理首页。

建议：

- `"/"` 默认跳转到企业页或登录页
- `"/_authenticated"` 的默认子路由改为企业页
- 登录成功后统一跳转到 `/enterprise`
- 401 会话失效后，重新回到 `/sign-in`

### 1.3 导航策略

企业管理页面应该成为 authenticated 区域的第一个、最显眼的入口。

建议：

- 企业管理放在侧边栏第一位
- 原来的 dashboard、users、keys、logs 等页面保留，但不再作为首页
- 这些旧页面只作为辅助入口，避免用户进来后先看到“旧控制台”

### 1.4 兼容策略

为了减少迁移风险，第一版不建议立刻删掉旧页面，只是：

- 改默认入口
- 改默认跳转
- 改导航顺序
- 把旧功能降级为次级入口

这样可以先把“企业版首页”跑稳，再逐步清理旧入口。

## 2. 角色与身份

这里建议把角色简单拆成三类：

- 企业主账户：负责企业总账、成员管理、统一计费
- 成员账户：属于某个企业，只管理自己的 API Key 和用量
- 系统管理员：用于运维和平台维护，不作为普通用户的默认入口

产品层面建议重点展示前两类，避免把“系统管理员”暴露成普通用户路径。

## 3. 简化注册方案

### 3.1 基本原则

注册流程只保留最小闭环：

- 只保留用户名、邮箱、密码、确认密码、邀请码
- 不做公开创建超级账户
- 第一个超级账户只通过初始化流程创建
- 普通成员默认通过邀请码注册
- 第一版不做 OAuth、Passkey、2FA、邮箱验证码、图形验证码

### 3.2 第一个超级账户

第一个超级账户建议仍然沿用初始化流程创建，而不是开放注册。

建议的初始化信息：

- 用户名
- 密码
- 确认密码
- 邮箱（可选）
- 企业名称（可选）

初始化完成后：

- 自动创建企业主账户
- 自动创建对应的企业记录
- 关闭初始化入口

### 3.3 普通成员注册

普通成员注册建议走“邀请码注册”。

建议表单字段：

- 用户名
- 邮箱（可选）
- 密码
- 确认密码
- 邀请码

注册成功后：

- 创建普通成员账号
- 绑定到对应企业
- 登录后直接进入企业管理页
- 成员只看到自己的 API Key、用量和日志

### 3.4 邀请码实现建议

为了尽量简单，第一版可以先复用现有的 `aff_code` / `inviter_id` 机制，不额外新增一套复杂的邀请码体系。

如果后续需要更完整的能力，再拆成独立的邀请表。

后续可扩展能力包括：

- 邀请码过期时间
- 单次使用
- 使用次数上限
- 邀请审计
- 指定成员角色

### 3.5 注册安全策略

即使流程变简单，也建议保留几个基础保护：

- 用户名唯一性检查
- 密码长度校验
- 邀请码有效性校验
- 接口限流
- 登录失败次数限制

这样可以先保证“简单可用”，再逐步增强安全性。

## 4. 页面结构建议

第一版建议保留以下页面入口：

- `/setup`：首次初始化
- `/sign-in`：登录
- `/register`：邀请码注册
- `/enterprise`：企业管理首页
- `/enterprise/members`：成员管理
- `/enterprise/usage`：企业用量
- `/enterprise/keys`：成员 API Key
- `/enterprise/logs`：企业日志

### 页面职责

- 企业管理首页：展示企业总览、成员数、用量、活跃 Key
- 成员管理：新增、禁用、删除成员
- 企业用量：按成员、Key、时间段查看消耗
- 企业日志：查看请求日志和计费归属

## 5. 推荐实施顺序

建议按这个顺序推进：

1. 修改默认首页和登录后的跳转
2. 让企业管理页成为 authenticated 区域默认落点
3. 把注册页简化为邀请码注册
4. 把初始化流程收敛为“只创建第一个超级账户”
5. 再逐步弱化或隐藏旧的 dashboard 风格入口

## 6. 待确认问题

为了后续实现更稳，下面几个点最好先定下来：

- 普通成员是否允许公开注册，还是只允许邀请码注册
- 邀请码是否只复用现有 `aff_code`，还是单独建表
- 旧 dashboard 是否完全隐藏，还是仅从主导航移除
- 初始化时是否同时创建企业名称
- 成员注册后是否允许自动加入某个默认企业，还是必须由企业主邀请

## 7. 初步结论

如果目标是“尽快把程序变成企业版入口”，我建议第一版采用：

- 首页默认进入企业管理
- 普通用户只保留登录 + 邀请注册
- 第一个超级账户仍然走初始化
- 旧功能先保留底层实现，但不作为默认入口

这样改动最小，路径最清晰，也方便后续继续收敛旧的登录/注册体系。
